概念层已经收口。核心判断——Evidence 而非 Candidate/Evaluator 才是稳定抽象——比同类 autonomous research framework 想得清楚。剩余风险几乎全部集中在同一个位置：软规则无法强制。read-mostly 契约、surrogate validity、comparability 判断、evidence 记录纪律，目前都靠 agent 自觉。下面 19 项按此排序。

结构性问题

这五项会让设计在实战中失败或静默退化，建议在写任何 SKILL.md 之前先定。

P0-1 改动量低
影响面全局

11 个 skill 与触发可靠性直接冲突

设计有 11 个 skill，靠 description 匹配触发。但 Codex 的 skill 列表有预算（约 context 的 2%，未知时约 8,000 字符），超预算时先截断 descriptions，再静默 omit。而 research-diagnosis / experiment-review / research-retrospective 三者的语义高度重叠——截断后触发会变得随机：要么都不触发，要么同时触发三个。

建议

V0 只发 3 个 skill（research-bootstrap / research-engineering / research-status），其余 8 个认知模式降级为 references/*.md，由主 skill 内一张路由表显式 Read。路由条件用状态谓词而非主题名：

| 观察到的状态                            | 加载                      |
|----------------------------------------|---------------------------|
| execution_status != completed 且无 result | (非 research 问题) 先 reconciliation |
| ≥2 live hypotheses 且刚完成一次 run      | references/experiment-review.md |
| 连续 N 次 iteration 无 belief change     | references/retrospective.md |
| 无 evaluator，或 local↑ 而 E4↓            | references/evaluation-design.md |
| 结论依赖 surrogate                       | references/surrogate-validity.md  # 强制 |

一个入口的显式路由表，比 11 条 description 的模糊匹配可靠得多。等确实需要 context 隔离或多 agent 时再升级为独立 skill。

P0-2 改动量低
影响面跨客户端

唯一能解决路由歧义的杠杆被可移植性设计掉了

Codex 支持在 agents/openai.yaml 里用 policy.allow_implicit_invocation 控制 skill 是否可被隐式触发——这正是压制 expert skill 过度触发所需要的机制。但附录 I 的 installer 做的是裸 copytree，而 §9.1 又要求 canonical skill 不含 client-specific frontmatter。结果是：能治 P0-1 的机制被"可移植性"排除在外。

同时，两份 copy 之间没有任何 drift 检测，必然漂移。

建议 
skills/<name>/
├── SKILL.md
├── references/
├── .claude/          # 可选覆盖层，仅用于生成副本
└── .agents/
    └── agents/openai.yaml

# installer 增加：
python tools/install_research_skills.py --check   # diff canonical vs installed，非零退出

overlay 只进生成副本，canonical 保持纯净；--check 可挂在 Gate 或 CI 上。没有 drift 检测，两份副本漂移是时间问题。

P0-3 改动量低
影响面Block Contract + KPI

belief-changing iteration 没有操作定义

这是全系统的原子单位——Block Contract 的 max_evidence_iterations、KPI 的 Evidence/hour 与 Validated unknowns/day 全靠它。但文档只给了语义描述（"改变技术判断的有效证据"），没有任何可审计的判据。AI 多算则 block 不设限，少算则提前收工。

建议

在 evidence record 里落成字段，让计数变成查询而非判断：

{
  "execution_status": "completed",
  "research_outcome": "refuted",
  "hypotheses_differentiated": ["H-037", "H-039"],
  "belief_delta": "H-039_eliminated",
  "counts_as_evidence_iteration": true
}
counts_as_evidence_iteration =
     execution_status == "completed"
 AND research_outcome IN {confirmed, refuted, inconclusive,
                          informative_failure, promising}
 AND (hypotheses_differentiated != [] OR belief_delta != "none")

Block Contract 的计数器只能由这个字段驱动，不允许 agent 自行判断。

P0-4 改动量中
影响面durable state 完整性

没有任何强制函数保证 evidence 真的被写入

整套 durable state 建立在"AI 每次 run 后都 append Evidence"这个纯自觉行为上。跑 5 个实验漏记 3 个，状态就静默腐烂——而且下一 session 无法发现，因为缺失的记录不会报错。

§14.2.1(5) 已经想到"commit 成功但 Evidence 尚未 append"的重叠场景，但没有把它一般化成检测器。

建议

§12.4 Reconciliation 增加两条确定性检查，由 researchlog reconcile 实现：

manifest.status == completed AND result.json 存在
  AND 无任何 Evidence 引用该 EXP-ID     → ORPHAN_RUN
                                          先补记，再开新研究

Evidence 引用不存在的 EXP-ID / EV-ID    → DANGLING_EVIDENCE

这是全篇投入产出比最高的一处补充：把"记录纪律"从自律变成可检测的不变量。

P0-5 改动量低
影响面Gate-2 可信度

Surrogate Validity Contract 是"在心里明确"

§6.5.3 说六项"AI 必须在内部明确；可写入 Evidence record，不要求生成单独文档"。"在内部明确"对 LLM 不可验证——模型可以声称做了。而 Gate-2 又依赖它来判定证据是否有效。

建议

改成 schema 硬约束。当 evidence_level < target_level 或 surrogate: true 时，surrogate_contract 为必填，researchlog validate 缺失即失败：

{
  "surrogate_contract": {
    "target_causal_claim": "...",
    "required_causal_features": ["..."],
    "preserved_features": ["..."],
    "missing_or_distorted_features": ["..."],
    "allowed_conclusions": ["..."],
    "forbidden_conclusions": ["..."],
    "verdict": "VALID_SURROGATE"
  }
}

把 prompt 纪律变成 schema 约束，是这份设计里最值得做的一类升级。

最高价值的新增机制

一条我认为应该无条件加进去的机制。当前设计里，它是唯一一个把主观判断保留在最关键位置的地方。

M-1 改动量中
收益高

invalidated_if：让可比性从判断变成查询

§6.5.4 的环境可比性契约要求 AI 主观判断 COMPATIBLE / REBASELINED / INCOMPARABLE。但可比性是证据自身的属性，不是需要临场推理的东西。

建议

evidence record 声明自己的失效条件：

{
  "evidence_id": "EV-0821",
  "invalidated_if": [
    "env.sim_physics_hz != 30",
    "inputs.replay_suite != recovery-12@sha256:...",
    "evaluator.version != eval-v3",
    "inputs.model != qwen-vl-72b@checkpoint:..."
  ]
}

于是 researchlog env <change> 可以确定性地输出：

$ researchlog env env-change-007.json
physics 30Hz -> 60Hz 使以下证据失效：
  EV-0031, EV-0044, EV-0821
其中 2 条支撑 FND-007 -> 建议降级为 Provisional
建议重跑 anchor: EXP-0118
连带收益
  • comparability 从判断变成查询——environment_change 一落地就知道要 rebaseline 哪几条 anchor
  • FINDINGS 的 confidence 可以被自动降级（支撑证据失效 → Provisional）
  • KPI 的 False-confidence rate 从人工统计变成可计算量
  • §22 里 "environment confound" 这一整类风险被大幅压缩

补充项

按性价比排序。每项都可独立决策，不依赖其他项。

ID位置问题建议决策
P1-1附录 GFINDINGS 条目只有 Confidence，没有 evidence level。§1.2 明确说"系统 E4 但新机制只有 E1"，但 schema 表达不出来。加 max_evidence_level: E2
P1-2§12.11只有 Established / Provisional / Refuted / Open。Refuted 是 hypothesis 的命运，不是 finding 的。缺"被推翻"状态，导致 KPI False-confidence rate 无法计算。加 SUPERSEDED + superseded_by + reason
P1-3§9.3CONSTRAINT/DECISION/VETO 的 source_text 设为"仅有诊断价值时保留"——但约束的措辞永远是语义承载的。"不要动 planner 的 recovery 分支"被规范化成 "do not modify navigation planner"，scope 就悄悄变了。非挑战型信号强制双语留存
P1-4§5.1DECISION FINAL 说"记录并执行"，但没说 AI 要先回述其规范化理解让你确认。VETO 被软化成 CONSTRAINT 是无声的。DECISION/VETO/CONSTRAINT 走一次 echo-back
P1-5§11.2声称"可粘贴给新 session 做 rehydration"，但整份是中文散文，AI 无法稳定提取 ACTIVE 状态。1–14 节中文 + 末尾英文 key 的 YAML block（maturity 三元组 / ACTIVE status / 关键 EV-ID / integrity）
P1-6§11.2它只报告不一致，然后"交给 research-engineering reconcile"——但它是最高频入口，你很可能只跑它。结果是不一致被报告但永不修复。末尾给 → 建议下一步: /research-engineering 执行 RECOVERY_RECONCILIATION
P1-7§10.3max_wall_clock_minutes 有了，但 agent 的真实货币是 token。20 分钟推理 + 300k token 的 probe 不叫 cheap。Block Contract 加 max_tokens
P1-8§10.3"到达边界后应 synthesize 当前 belief" 未编码，退出无产物要求。block 关闭前强制写 belief_delta: none | refined | overturned 到 CURRENT
P1-9§12.9比赛提交次数通常只有 3–5 次，但 V0 完全不 gate。bootstrap 写入 BOUNDARIES.md: submission_budget: N，每次消耗前必须升级
P1-10§14.14隔离表格从 E0/E1 直接跳到 E4/E5。而 E2/E3 正是 proxy overfit 发生的地方——§22 自己也列了这个风险。补一行：frozen replay snapshot + hash + dev/holdout 只读分离
P1-11§20.1V0 验收 22 条不可能一天完成，且多数需要工具才能测。拆成 Day-1 must（5 条）与 V0 complete
P1-12§12.14EVIDENCE.jsonl → sharded 的迁移正是 18 号不变量想避免的无谓 schema churn，而 V0 做几乎零成本。第一天就 shard；orphan detector 也更好写

建议推后

D-1 类型减少 V0 面积

跨客户端对称性在 V0 被过度投资

§9 / §26 花了很多篇幅保证 Codex 与 Claude Code 等价。方向是对的——canonical skills/ + 双份 copy 是正确的选择——但 V0 不应该为"第二个客户端"写任何专属内容。

否则你会在还没验证主循环是否成立时，先解决一个次要的兼容性问题。

建议

先用一个客户端把 research semantics 跑通，另一个只做 §26.3 的 cross-client handoff 验收。P0-2 的 overlay 机制已经为后续差异化留好了位置。

实现设想

核心判断：SKILL.md 是提示词胶水，真正可验证的产品是 JSON schema。所以构建顺序反过来。

构建顺序 · 一天
  1. 先写 schema + researchlog.py validate，用 TDD。这是唯一该用 TDD 的地方——deterministic bookkeeping，不是 research。这顺便演示了 Research/Integration 双模式的分界线：工具是长期资产，值得工程化；研究是一次性的。这个划分本身就是对设计的一次检验。
  2. AGENTS.md（≤150 行，只放路由 + 不变量 + 语言规则）+ CLAUDE.md（仅 @AGENTS.md）。
  3. 3 个 SKILL.md + references/*.md。
  4. 7 个状态文件 skeleton，由 researchlog init 生成，全部带 schema_version。
  5. Session recovery 测试 harness。

唯一的验证实验

§12.16 的失忆测试是整套设计唯一的客观检验。建议第一天就把它做成可执行脚本，其余 17 条 V0 验收项都是在这条通过之后才有意义。

A启动 /research-engineering，跑到 ACTIVE=running 中途，kill 客户端
B新 session，不给任何旧聊天，只给 repo
✓找到正确 branch / HEAD
✓理解 dirty diff 的意图
✓知道 pending cases
✓不重复启动已有 run
✓选择与 A 一致的 next action
↺反向再跑一次（换客户端）
